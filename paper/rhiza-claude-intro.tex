\begin{abstract}
\noindent
\textbf{rhiza-claude} is a Claude Code plugin for repositories that share their
scaffolding with a template repository instead of each carrying a private copy of it.
% rhiza-count: commands
This document is the part the reference pages cannot be: not a catalogue of the ten
skills under \file{skills/}, but an account of the problem they exist to
solve --- the two-repository boundary a sync respects, what ``rhiza-managed'' actually
means on disk, the order the commands are meant to be run in, and why a plugin whose
selling point is determinism keeps half of itself in prose. It covers installation,
compares the design against the obvious alternative of shipping an MCP server, and
closes with a worked first run: empty directory to a managed, synced, scored
repository. The figures throughout are captured output, not mock-ups.
\end{abstract}

\section{The problem}

Ten repositories need substantially the same scaffolding. Continuous integration
workflows, a \file{Makefile}, lint and type and coverage gates, a documentation build,
a licence, a release path. None of it is the interesting part of any of those ten
projects, and all of it has to exist before the interesting part can be trusted.

The obvious approach --- write it once, copy it into each repository --- fails slowly
rather than loudly. A workflow gets fixed in one repository and not the other nine. A
coverage threshold gets lowered under deadline in a repository nobody revisits. Two
years later there is no answer to the question \emph{which repositories have the
current gates}, because nothing anywhere records which vintage of the scaffolding each
one received.

\textbf{rhiza} is that scaffolding kept once, in a \emph{template repository}:
\href{https://github.com/jebel-quant/rhiza}{\texttt{jebel-quant/rhiza}}, one
multi-language template serving Python, Rust and Go alike. The language you pick selects
a \emph{profile} within it (\texttt{github-project}, \texttt{rust-local},
\texttt{go-local}), never a different repository --- see \S\ref{sec:languages}.
\textbf{rhiza-claude} --- this plugin --- is how an
individual repository adopts that template, keeps up with its releases, and is told how
well it is doing against the gates the template delivers.

Two things follow from that framing, and they are the reason an introduction is needed
at all. First, there are always \emph{two} repositories in play, and almost every
question a newcomer has is really a question about the boundary between them. Second,
the interesting work is not the copying --- it is knowing precisely which files are the
template's to overwrite and which are yours to keep.

\section{The two-repository model}

\begin{center}
\begin{tabular}{@{}p{0.30\linewidth}p{0.36\linewidth}p{0.26\linewidth}@{}}
\toprule
& \textbf{owns} & \textbf{who changes it} \\
\midrule
\textbf{the template} &
CI stubs, \file{Makefile}, \file{.rhiza/rhiza.mk}, the docs base &
upstream --- you receive it \\[0.4em]
\textbf{your repository} &
source, tests, \file{pyproject.toml}, README prose &
you --- the sync never touches it \\
\bottomrule
\end{tabular}
\end{center}

\noindent
A sync is therefore \emph{not} a copy of the template over your repository. \cmd{update}
writes only template-owned paths, and it knows which paths those are because the
previous sync wrote them down. Your \file{src/} is not in that set, so it cannot be
swept in --- there is no blanket \texttt{git add -{}-all} anywhere in the flow, which is a
deliberate design constraint rather than an implementation detail.

\noindent
The dashed boundary is your repository; the arrow is the only thing a sync does. Nothing

\section{What ``rhiza-managed'' means}

It means two files under \file{.rhiza/}, and they answer different questions.

\begin{center}
\begin{tabular}{@{}p{0.24\linewidth}p{0.34\linewidth}p{0.34\linewidth}@{}}
\toprule
\textbf{file} & \textbf{it is} & \textbf{question it answers} \\
\midrule
\file{template.yml} & a \textbf{pointer}: template repository and pinned \texttt{ref} & what \emph{would} we sync from? \\[0.4em]
\file{template.lock} & a \textbf{record}: repository, ref, commit SHA, timestamp, strategy, every managed file & what \emph{was} delivered, and when? \\
\bottomrule
\end{tabular}
\end{center}

\noindent
\textbf{Intent versus outcome.} The two disagree in both directions, which is the whole
reason both exist. A freshly initialised repository has a valid pointer and no lock at
all (Figure~\ref{fig:unsynced}). A long-synced repository can carry a lock beside a
pointer somebody has since broken by hand. Reporting either one alone is misleading, so
\cmd{status} always reports both halves.

\termfig{fig-unsynced.png}{\linewidth}{%
  The two halves disagreeing, which is the normal state after \cmd{init}. Validation
  passes --- the pointer is well-formed and names a real template --- while
  \file{template.lock} does not exist, because nothing has been synced yet. A tool that
  reported only the first line would call this repository healthy; one that reported
  only the second would call it broken. It is neither: it is \emph{managed but not yet
  synced}.}{fig:unsynced}

The same distinction is load-bearing for \cmd{quality}. Before anything else it looks
for \emph{both} of those files. Every gate in its list is a \texttt{make} target that
the sync delivers, so running them against a managed-but-unsynced repository would
report it as \emph{broken} when it is merely \emph{unsynced} --- a wrong answer rather
than a missing one.

What it \emph{does} with that distinction is the part that has changed. It used to
refuse outright. Now either file being absent puts it into a \emph{degraded mode}: the
template-delivered gates are skipped, whatever targets the repository's own makefile
provides are run instead, and the design work is scored in full. The wrong answer is
still avoided, because a skipped gate is marked unavailable rather than failed --- but
the half of the assessment that never needed the template is no longer discarded along
with it. A degraded run says as much in its own output, since its number rests on a
narrower base and is not comparable to a managed repository's. By contrast
\cmd{release} needs neither file: it reads \texttt{[tool.bumpversion]} from the
repository itself, so it works on any git repository at all --- this plugin included.

\section{Installing the plugin}

Nothing above is reachable until Claude Code knows the plugin exists. Installation is
two lines, typed inside Claude Code:

\begin{lstlisting}
/plugin marketplace add Jebel-Quant/rhiza-claude
/plugin install rhiza@rhiza-claude
\end{lstlisting}

\noindent
The first line registers the \emph{marketplace} --- this repository, read straight from
git; the second installs the \emph{plugin} it publishes. From a shell, \texttt{make
install} runs the equivalent \texttt{claude plugin} commands, which is the form to
% rhiza-count: commands
prefer in a setup script. Either way the ten commands then appear namespaced under
\texttt{/rhiza:}, and typing \texttt{/rhiza} is enough for Claude Code to autocomplete
them.

\subsection*{Pinning a version}

By default the marketplace tracks this repository's default branch, so \texttt{/plugin
install} gives you the latest release. Pinning happens at the \emph{marketplace} layer
rather than per plugin --- append the version's git tag as a \texttt{\#<ref>} suffix when
adding the marketplace:

\begin{lstlisting}
/plugin marketplace add Jebel-Quant/rhiza-claude#v0.11.0
/plugin install rhiza@rhiza-claude
\end{lstlisting}

\noindent
Once the marketplace is added, \texttt{/plugin install} uses whatever ref it points at,
so switching versions means removing the marketplace and re-adding it at the tag you
want. This is worth knowing because it mirrors the model the plugin itself applies to
your repositories: a pinned ref, changed deliberately, rather than a floating
\texttt{latest}.

\medskip
\noindent
The one thing to install \emph{outside} Claude Code is \texttt{uv}, and even that is
optional up front --- both \cmd{init} and \cmd{update} check for it as their first step
and offer to install it. There is no \texttt{rhiza} CLI; see
\S\ref{sec:requirements}.

\section{The intended path}

\begin{center}
\begin{tikzpicture}[
  node distance=6mm,
  stepbox/.style={draw=leaf!45, fill=leaf!8, rounded corners=2pt, align=center,
               font=\small, inner sep=5pt, text width=27mm},
  gate/.style={align=center, font=\tiny\color{slate}, inner sep=1pt},
  arrow/.style={-{Stealth[length=2.2mm]}, draw=slate!70},
]
\node[stepbox] (a) {empty or existing repo};
\node[stepbox, right=10mm of a] (b) {\cmd{init}\\[0.15em]\footnotesize PR \#1};
\node[stepbox, right=10mm of b] (c) {\cmd{update}\\[0.15em]\footnotesize PR \#2};
\node[stepbox, right=10mm of c] (d) {\cmd{quality}\\[0.15em]\footnotesize scorecard};
\draw[arrow] (a) -- (b);
\draw[arrow] (b) -- node[gate, above] {merge} (c);
\draw[arrow] (c) -- node[gate, above] {merge} (d);
\end{tikzpicture}
\end{center}

Three commands, two pull requests you merge yourself, in that order:

\begin{enumerate}[leftmargin=1.4em, itemsep=0.35em]
  \item \cmd{init} writes exactly one file of its own --- \file{.rhiza/template.yml} ---
        and \textbf{deliberately syncs nothing}. No CI, no \file{Makefile}, no gates
        arrive at this step.
  \item \cmd{update} performs the first sync. This is what brings the template content
        in and what writes \file{.rhiza/template.lock}.
  \item \cmd{quality} needs that content to exist as real \texttt{make} targets, so it
        comes third.
\end{enumerate}

\noindent
Running them out of order is not dangerous --- each stops early and says why --- but the
sequence is worth knowing in advance, because \emph{``\cmd{init} ran and no CI
appeared''} is the expected outcome of step one rather than a failure. Separating the two
pull requests is the point: the file that declares which template you follow is
reviewable on its own, apart from the several dozen files that template then delivers.

\section{A worked first run}

\subsection*{0. A git repository with a remote}

\begin{lstlisting}
mkdir my-lib && cd my-lib && git init
gh repo create my-lib --private --source=. --push   # or create it in the UI
\end{lstlisting}

\noindent
\cmd{init} never pushes to your default branch. If the repository does not exist
upstream yet it asks \emph{you} to create it --- an empty README is enough --- rather
than pushing one itself. Then start Claude Code in that directory.

\subsection*{1. \cmd{init} --- become rhiza-managed}

It detects platform, owner and name from \texttt{origin} (asking when it cannot), picks
the language and template repository, resolves the template's latest release as the
initial pin, and opens a pull request on a \texttt{rhiza\_init\_<date>} branch:

\begin{center}
\begin{tabular}{@{}p{0.32\linewidth}p{0.60\linewidth}@{}}
\toprule
\textbf{written by} & \textbf{file} \\
\midrule
the command itself & \file{.rhiza/template.yml} --- the pointer and pinned ref \\
the skeleton procedure & \file{pyproject.toml} (via \texttt{uv init -{}-lib}), \file{src/}, \file{.python-version} \\
the license procedure & \file{LICENSE} plus the SPDX metadata in \file{pyproject.toml} \\
\bottomrule
\end{tabular}
\end{center}

\noindent
There is no \file{.rhiza/template.lock} yet, and no workflows (Figure~\ref{fig:init}).
Merge the pull request.

\termfig{fig-init.png}{0.94\linewidth}{%
  Step one, driven through the bundled scripts the command delegates to. Six files are
  staged and \file{.rhiza/} contains exactly one of them --- the pointer. No lock, no
  \file{Makefile}, no \file{.github/workflows/}: this is the expected outcome of
  \cmd{init}, not a failure of it.}{fig:init}

\subsection*{2. \cmd{update} --- the first sync}

It bumps the \texttt{ref} in \file{template.yml} to the newest template release, syncs,
resolves any conflict by taking the upstream side, and opens a second pull request
carrying the template-owned files --- \file{.github/workflows/}, \file{Makefile},
\file{.rhiza/rhiza.mk}, the docs base --- together with \file{.rhiza/template.lock}
recording exactly what was delivered. Only paths the lock names are staged, so nothing
of yours is included even if it changed in your working tree. Merge that too.

\subsection*{3. \cmd{status} --- confirm both halves}

\begin{lstlisting}
/rhiza:status --files
\end{lstlisting}

\noindent
Read-only. It validates the pointer \emph{and} prints what the lock records: repository,
ref, commit SHA, timestamp, strategy, and with \texttt{-{}-files} the managed files as a
tree (Figure~\ref{fig:status}). This is how you distinguish \emph{managed and synced}
from \emph{managed but never synced} --- compare it against
Figure~\ref{fig:unsynced}, which is the same command on a repository that has only
been initialised.

\termfig{fig-status.png}{0.74\linewidth}{%
  A synced repository reporting both halves. The six header lines come from the lock, so
  they describe what actually arrived --- including the commit SHA, which pins the answer
  to \emph{which vintage of the scaffolding does this repository have}. The tree below is
  the set of managed files: every path the sync owns and may overwrite, and by omission,
  everything that is yours.}{fig:status}

\subsection*{4. \cmd{quality} --- get scored}

Now that the gates exist, this runs them --- lint, types, documentation, dependencies,
security, tests, test layout, complexity, architecture --- and produces a 1--10
scorecard with findings and an optional menu to file them as issues. It proposes fixes
and applies none.

\medskip
\noindent
Afterwards: \cmd{update} again whenever the template cuts a release
(\texttt{-{}-check} compares your pin against the latest, as in
Figure~\ref{fig:check}), \cmd{docs} to create or refresh \file{README.md},
\file{CLAUDE.md} and \file{mkdocs.yml} (preserving hand-written prose), and
\cmd{release} when you want to cut a version.

\termfig{fig-check.png}{0.9\linewidth}{%
  \texttt{-{}-check} adds one line to the report: the pinned ref, the latest upstream
  release, and the distance between them. This is the question the copy-paste approach
  cannot answer for any repository, and the reason the lock records a ref at all.}{fig:check}

\section{Commands and procedures}

The plugin ships two kinds of markdown, and the distinction is enforced rather than
conventional:

\begin{itemize}[leftmargin=1.4em, itemsep=0.3em]
  \item \file{skills/<name>/SKILL.md} are \textbf{slash commands} you invoke: ten of
        them, each with a reference page. The \emph{directory} carries the name, so the
        file that answers \cmd{init} is \file{skills/init/SKILL.md}.
  \item \file{prompts/*.md} are \textbf{internal procedures}: eight shared steps a
        command reaches with the \texttt{Read} tool, kept deliberately \emph{outside}
        \file{skills/} so they cannot be invoked directly.
\end{itemize}

\noindent
That second point is the load-bearing one, and it is why \file{prompts/} sits where it
does. Claude Code discovers components by looking for particular directory names at the
plugin root --- \file{skills/} and \file{hooks/} are two of them, and this plugin ships
both. \file{prompts/} is deliberately \emph{not} one of them: a procedure placed there
cannot be reached as a slash command, which is a guarantee about the surface rather than
a filing preference.

\medskip
\noindent
Procedures are not implementation trivia, and filing them under ``internals'' undersells
them: they are where the shared behaviour lives, which is why
\file{skills/init/SKILL.md} alone does
not explain what \cmd{init} does. Installing \texttt{uv}, choosing a work branch off an
untouched default, scaffolding a \file{pyproject.toml}, pinning a Python version, writing
a licence, gathering design evidence, applying the scoring rubric, recording which
upstream failures are known --- each is a procedure, and that is
exactly why \cmd{init} and \cmd{update} behave identically everywhere they overlap. Nor
can they be folded into the skills that read them: \file{pr-base} is read by three
commands and \file{install-uv} by two, so a shared procedure has no single skill folder
to live in.

\medskip
\noindent
A check in CI enforces the arrangement, in six rules: every procedure declares that it
is not a slash command, none carries command frontmatter, none collides with a command
name, every referenced procedure path resolves, none is orphaned --- and, the sixth, no
shipped prose names a discovery location this plugin does not have. That last rule gates
the \emph{reasoning} rather than the wiring. Rules one to five will happily pass a file
that explains itself by arguing against a directory which no longer exists, and an
argument from an absent constraint reads, to a later human or model, as a constraint that
no longer binds.

\section{The ten commands, and what each writes}

An introduction should say which of these change your repository, because that is the
first thing anyone actually wants to know.

\begin{center}
\small
\begin{tabular}{@{}p{0.23\linewidth}p{0.37\linewidth}p{0.32\linewidth}@{}}
\toprule
\textbf{command} & \textbf{what it does} & \textbf{what it writes} \\
\midrule
\cmd{init} & make the repository rhiza-managed; no sync, no gates &
one file of its own, then a pull request \\[0.35em]
\cmd{update} & sync to a template release, upstream side wins conflicts &
template-owned paths only, then a pull request \\[0.35em]
\cmd{quality} & run the gates and score 1--10 with findings &
nothing --- proposes fixes, applies none \\[0.35em]
\cmd{docs} & create or refresh \file{README.md}, \file{CLAUDE.md}, \file{mkdocs.yml} &
those files; no commit, no pull request \\[0.35em]
\cmd{release} & pick a next version from a table, bump, changelog &
a release pull request, then a tag on the merged commit \\[0.35em]
\cmd{remote} & read what CI on the origin said, then fix the red requests &
commits on the request's own branch; never the default one \\[0.35em]
\cmd{status} & report the pointer \emph{and} the lock &
nothing --- read-only \\[0.35em]
\cmd{maffay} & print one bonmot from a random Peter Maffay song &
nothing --- needs no repository at all \\[0.35em]
\cmd{completions} & install shell tab-completion for \texttt{make} targets &
files in your data directory, never in the repository \\[0.35em]
\cmd{detach} & delete every file the lock records, prune empty dirs &
removes files; confirms first \\
\bottomrule
\end{tabular}
\end{center}

\noindent
Two patterns are worth reading off that table. The commands that change a \emph{shared}
repository do it through a pull request you review --- none of \cmd{init}, \cmd{update}
or \cmd{release} pushes to your default branch. \cmd{release} was the last to join them:
it used to commit the version bump directly and hand back a tag to push, which meant the
one commit deciding what ships was the one commit no required check had gated. And the
ones that assess rather than act
(\cmd{quality}, \cmd{status}) write nothing at all, which is what makes them safe to run
on a repository you have just inherited and do not yet understand.

\medskip
\noindent
Four commands sit outside the sequence entirely, and it is worth saying why they are
here. \cmd{release} needs no \file{.rhiza/} at all --- it reads the repository's own
\texttt{[tool.bumpversion]} configuration, so it works on any git repository, this plugin
included. \cmd{remote} needs none either: it asks the forge what continuous integration
said about the open requests, and an unmanaged repository has requests and a build like
any other. It is also the one command that reads a fact this plugin cannot derive
locally --- \emph{local green and origin green are different claims, and only the second
one merges} --- which is why it is the only one that touches CI at all.
\cmd{maffay} needs even less: no repository, no git, no template. It draws a
line from a Peter Maffay song and prints it, which is the whole command. It earns its
place because the song is drawn by a \emph{script} rather than by the model --- asked to
choose at random, a model reaches for the same few favourites --- and that makes it the
smallest complete illustration of this plugin's central split: even picking at random is
deterministic work, so it belongs in tested code. \cmd{completions} is outside for a
different reason: it installs \texttt{make} tab-completion into your shell's data
directory, so it needs no \file{.rhiza/}, works in any \texttt{make} project, and is the
only command that writes outside the repository it is run in.

\subsection*{Common confusions}

\begin{description}[leftmargin=0pt, style=nextline, itemsep=0.35em]
  \item[``\cmd{init} finished but no CI appeared.'']
        Correct behaviour. \cmd{init} writes the pointer; \cmd{update} performs the
        first sync. The template content arrives in the second pull request.
  \item[``Which CLI do I have to install?'']
        None. \texttt{uv} is the only hard dependency; the plugin's own scripts are
        stdlib-only Python. There is no \texttt{rhiza} CLI in this picture.
  \item[``Can I edit a synced file?'']
        You can, but \cmd{update} resolves conflicts by taking the upstream side, so
        your edit is expected to lose. Template-owned files are changed
        \emph{upstream}; that is the point of having one original.
  \item[``Will a sync overwrite my README?'']
        No. \file{README.md} is yours, not template-owned. \cmd{docs} is the only
        command that writes it, and it preserves hand-written prose --- it replaces the
        generated badge block and corrects stale facts, but never deletes what a human
        wrote.
  \item[``\cmd{quality} scored me on almost nothing.'']
        It found no \file{.rhiza/rhiza.mk} --- managed but never synced, or not managed
        at all --- so it ran in degraded mode. The template's gates are skipped rather
        than failed, because scoring a missing gate would report it as a failure of your
        code. Run \cmd{update} first for the full assessment; the degraded score is real,
        but it rests on your own \texttt{make} targets and the design analysis alone, and
        it says so.
\end{description}

\section{Why the commands are prose}

The split is deliberate: \textbf{deterministic work belongs in tested code, judgement
belongs in markdown.}

The bundled Python under \file{scripts/} does the parts with exactly one right answer
--- parsing the lock, merging synced files, comparing versions as semver, computing the
legal candidate bumps --- and it is stdlib-only, strictly type-checked, and held at
100\,\% test coverage. The markdown does the parts that require a reading of your
repository: which findings matter, whether a breaking change should spend the 1.0
signal, what to preserve in a README a human wrote.

Two consequences are worth stating, because they are what make the arrangement more than
a slogan. First, \emph{the prose is gated too}: a command that names a script, a flag or
another command which no longer exists fails the build rather than failing in front of a
user mid-task. Second, where a model would reliably guess badly, the guess is removed
rather than improved --- \cmd{release} lays the legal next versions out as a table and
declines to recommend one (Figure~\ref{fig:release}), because whether \texttt{0.x} should
become \texttt{1.0.0} is an intention about API stability that no commit log records.

\termfig{fig-release.png}{0.92\linewidth}{%
  The division of labour in one screen. Computing the candidates is arithmetic over
  semver and belongs in tested code: the script derives them, and enforces the floor that
  keeps a release from going backwards. Choosing among them is a judgement about API
  stability, so the script stops --- \texttt{listing suggestions only} --- and the choice
  is the user's.}{fig:release}

\section{Compared with an MCP server}

The obvious alternative design is not a plugin at all. The Model Context Protocol is the
standard way to give a model capabilities it does not otherwise have: you run a
\emph{server} --- a local subprocess speaking over stdio, or a remote endpoint behind a
URL --- and it advertises typed tools that any MCP-capable host can discover and call.
Shipping rhiza as \texttt{rhiza-mcp} exposing \texttt{rhiza\_sync},
\texttt{rhiza\_status} and \texttt{rhiza\_score} would be a perfectly conventional
choice. It is worth being explicit about why this is a plugin instead, because the
reasoning generalises past this project.

\begin{center}
\small
\begin{tabular}{@{}p{0.20\linewidth}p{0.36\linewidth}p{0.36\linewidth}@{}}
\toprule
& \textbf{an MCP server} & \textbf{this plugin} \\
\midrule
\textbf{what ships} & a program, plus a transport &
markdown and stdlib scripts \\[0.35em]
\textbf{at rest} & a process or endpoint to run, version and reach &
files in a git repository \\[0.35em]
\textbf{interface} & a tool schema, fixed at the boundary &
prose the model reads \\[0.35em]
\textbf{reach} & whatever the server can talk to &
whatever the host already can \\[0.35em]
\textbf{portability} & any MCP host &
Claude Code only \\
\bottomrule
\end{tabular}
\end{center}

\noindent
\textbf{The deciding question is reach.} An MCP server earns its keep when it can touch
something the host cannot: a hosted service, a database, an internal API whose
credentials have no business being in a shell. Everything rhiza operates on is already
under the host's hand --- \texttt{git}, \texttt{make}, the filesystem,
\texttt{gh}/\texttt{glab}. A server wrapping those would add a process, a lifecycle, and
a schema without adding a single capability; the same \texttt{git} commands would run,
one indirection further away. Worse, the interesting half of this plugin does not fit
through a tool schema at all. \cmd{quality} is a reading of your repository and
\cmd{docs} preserves prose a human wrote --- neither is a function call with arguments,
and a typed boundary is the wrong shape for judgement.

\medskip
\noindent
\textbf{Where an MCP server would be the better answer.} Three cases, none of which this
plugin is:

\begin{itemize}[leftmargin=1.4em, itemsep=0.3em]
  \item \textbf{A boundary worth enforcing.} If the operation needed authorisation,
        auditing or rate limiting, a narrow typed surface beats handing the model a
        shell. rhiza needs none of that: the destructive commands go through a pull
        request you review, which is the boundary.
  \item \textbf{State that outlives one repository.} \emph{Which of our thirty
        repositories are behind, and by how many releases?} is a fleet question. Answering
        it means reading thirty locks and holding the result somewhere --- genuinely
        server-shaped work, and a plausible companion to this plugin rather than a
        replacement for it. Notice it would consume exactly the same
        \file{template.lock} files; the per-repository commands would not change.
  \item \textbf{Other clients.} MCP is client-agnostic and a plugin is not. If these
        workflows had to run from several editors, or from CI with no Claude Code present,
        the protocol would be the reason to pay for a server.
\end{itemize}

\noindent
That last point is the honest cost of the choice made here, and it should not be
glossed: \textbf{this plugin works in Claude Code and nowhere else.} What buys back the
price is that the plugin is content rather than infrastructure. There is nothing to run,
nothing to keep alive, and no version skew between a server and the repository it acts
on --- the behaviour \emph{is} a set of files, reviewable as a diff, pinned by a git ref,
and gated by the same CI that checks the scripts. For a tool whose entire subject is
keeping many repositories honest about which version of something they have, that
symmetry is not an accident.

\section{What it needs, and what it is not}
\label{sec:requirements}

\textbf{\texttt{uv} is the one hard dependency}, and both \cmd{init} and \cmd{update}
offer to install it as their first step. \texttt{git} and \texttt{make} are used and are
near-universal. The plugin's own scripts are stdlib-only Python: \textbf{there is no
\texttt{rhiza} CLI to install}, which is the most common point of confusion about what
this actually requires.

% rhiza-count: commands procedures
Honest scope, at v0.11.0: ten user-facing commands, eight internal procedures. It is
not a build system, a package manager, or a replacement for your CI --- the template
delivers workflows, and the plugin's job is to get them to you intact and tell you how
the result scores. Nothing here runs on a schedule or in the background; every command
is something you invoke, and the two commands that change a shared repository
(\cmd{init}, \cmd{update}) do it by opening a pull request you review.

\subsection*{Three languages, one template}
\label{sec:languages}

\cmd{init} offers Python, Rust and Go, and all three point at the same multi-language
template. The language chooses a \emph{profile} inside it --- \texttt{github-project},
\texttt{rust-local}, \texttt{go-local} --- never a different repository, which is worth
stating because ``a template per language'' is the natural assumption and it is wrong.

They are not equally supported, and the difference is better known before the bootstrap
than after. All three initialise, sync, report and release identically. What differs is
the far end: \textbf{Rust and Go have no hosted CI workflows yet}, and \cmd{quality}'s
gate list \emph{is} the Python profile --- the one this plugin has actually been run
against. On a Rust or Go repository it instead probes the \file{Makefile} for the targets
that are really there, scores those, and marks the language-specific subcategories
out-of-scope.

That is a deliberate trade rather than an unfinished edge. A hand-written table of gates
for a profile the plugin has never run against would be prose asserting what it cannot
back; discovery degrades honestly where a guessed table would simply lie. The cost is
real and \cmd{quality} states it in its own output: a Rust or Go scorecard rests on a
narrower base than a Python one, and the report says which gates it found and which
subcategories it skipped.

\section{Glossary}

The words that carry the model, in one place. Each is used above in exactly this sense.

\begin{description}[leftmargin=0pt, style=nextline, itemsep=0.3em]
  \item[template repository]
        The upstream repository holding the shared scaffolding ---
        \texttt{jebel-quant/rhiza}, or a fork of it. One repository serves Python, Rust
        and Go; the language selects a profile within it. You read from it; you do not
        sync \emph{to} it.
  \item[profile]
        The subset of the template a language takes: \texttt{github-project},
        \texttt{rust-local}, \texttt{go-local}. Chosen at \cmd{init}, recorded in the
        pointer, and the reason three languages need only one template.
  \item[pointer --- \file{template.yml}]
        Declared intent: which template repository, and which pinned \texttt{ref}. The
        one file \cmd{init} writes itself, and the file \cmd{update} bumps.
  \item[lock --- \file{template.lock}]
        Recorded outcome: repository, ref, commit SHA, timestamp, strategy, and the list
        of managed files. Written by a sync, never by hand.
  \item[managed file]
        A path the lock names --- template-owned, and therefore the sync's to overwrite.
        Everything not in that list is yours, and no command stages it.
  \item[rhiza-managed vs.\ synced]
        \emph{Managed} means the pointer exists. \emph{Synced} means the content
        arrived, which is observable as \file{.rhiza/rhiza.mk}. Both are required by
        \cmd{quality}, and the gap between the two is the state \cmd{init}
        deliberately leaves you in.
  \item[skill --- \file{skills/<name>/SKILL.md}]
        The file behind one slash command. Claude Code discovers it by scanning
        \file{skills/} at the plugin root, and takes the command name from the
        \emph{directory}, so \file{skills/init/SKILL.md} answers \cmd{init}.
  \item[procedure --- \file{prompts/}]
        A shared step a command reaches with the \texttt{Read} tool. \file{prompts/} is
        not a directory Claude Code scans, which is exactly why procedures live there:
        one cannot be invoked as a slash command.
  \item[gate]
        A \texttt{make} target delivered by the sync that either passes or fails: lint,
        types, docstring coverage, tests, dependency and security checks, test layout.
  \item[scorecard]
        What \cmd{quality} produces: a 1--10 mark per category with findings, plus an
        optional menu to file them as issues. Assessment only --- it applies no fixes.
\end{description}
